# Repository Guidelines

## Project Structure & Module Organization

This is a ROS 2 workspace. Its package lives in `src/tf_lisense_pkg`:

- `src/` contains ROS 2 node implementations, currently `odom_listener_node.cpp`.
- `include/tf_lisense_pkg/` contains reusable C++ headers, including the Linux serial-port wrapper and frame encoder.
- `CMakeLists.txt` defines targets and dependencies; `package.xml` declares package metadata.
- `build/`, `install/`, and `log/` are generated by `colcon`; do not edit them.

Keep new node sources in `src/` and public headers under `include/tf_lisense_pkg/`. Add every new executable and dependency to both package manifests where required.

## Build, Test, and Development Commands

From the workspace root, source ROS 2 and build only this package:

```bash
source /opt/ros/<distro>/setup.bash
colcon build --packages-select tf_lisense_pkg
source install/setup.bash
ros2 run tf_lisense_pkg odom_listener_node
```

Pass runtime parameters explicitly when hardware differs:

```bash
ros2 run tf_lisense_pkg odom_listener_node --ros-args -p serial_device:=/dev/ttyUSB0 -p filter_alpha:=0.3
```

Use `colcon test --packages-select tf_lisense_pkg` and `colcon test-result --verbose` after tests are added. Check the input topic with `ros2 topic echo /lio/imu/odom` before hardware testing.

## Coding Style & Naming Conventions

Use C++17 and retain the project’s four-space indentation and brace-on-new-line style. Name classes in `PascalCase` (`OdomListener`), functions in `camelCase` (`quaternionToYaw`), and member fields with the existing `m_` prefix. Prefer `constexpr`, `const`, and fixed-width integer types for protocol values. Keep ROS parameters configurable instead of hard-coding device paths or topic names. The compiler enables `-Wall -Wextra -Wpedantic`; resolve warnings rather than suppressing them.

## Testing Guidelines

No automated test framework is configured yet. Add focused `ament_cmake` tests for new conversion, filtering, or serial-frame logic; name source files after the behavior, for example `test_serial_sender.cpp`. For node changes, confirm the subscribed topic, parameter values, log output, and the expected `0xAA ... 0xBB` serial frame using safe hardware or a mock device.

## Commit & Pull Request Guidelines

No Git history is available in this checkout, so use concise imperative commits such as `Add yaw filter parameter`. Keep each commit scoped to one behavior. Pull requests should describe the ROS topic/parameters affected, build and test commands run, hardware assumptions, and include relevant terminal output or serial captures. Never commit device-specific secrets or credentials.
